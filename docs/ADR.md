# Architecture Decision Records

## 철학
MVP 속도 최우선. 별도 인프라나 추상화보다 작동하는 최소 구현을 선택한다. 검증이 필요한 아키텍처 가정(지연시간, 토큰 사용량 등)은 배포 직전이 아니라 해당 기능을 구현하는 시점에 스파이크로 먼저 확인한다.

---

### ADR-001: Next.js App Router + Vercel CLI로 조기·잦은 배포
**결정**: Next.js 15 App Router를 사용하고, Vercel에 Vercel CLI(`vercel deploy`)로 배포한다. 기능이 없는 mock/스켈레톤 상태부터 가장 먼저 배포하고, 이후 각 개발 단계를 완료할 때마다 재배포한다.
**이유**: 랜딩/대시보드/API를 단일 배포 단위로 묶을 수 있고 Vercel과 궁합이 좋다. 조기·잦은 배포로 환경변수 누락, 함수 실행시간 제한 같은 배포 파이프라인 이슈를 개발 후반이 아니라 초반에 발견할 수 있다.
**트레이드오프**: Vercel 서버리스 함수의 실행시간 제약이 동기 CSV 분석과 상충할 수 있다 — `maxDuration`을 스파이크로 실측해 대응한다(ADR-003 참고).

### ADR-002: Supabase 단일 백엔드
**결정**: 인증(Google OAuth), 데이터베이스(Postgres), 파일 저장(Storage)을 Supabase 하나로 통합한다.
**이유**: MVP 속도가 최우선이라 별도 인프라를 관리할 필요가 없고, RLS로 사용자 간 데이터 격리를 선언적으로 구현할 수 있다.
**트레이드오프**: 벤더 락인.

### ADR-003: Claude는 컬럼 매핑 + 카테고리 분류만, 행 단위 변환은 코드
**결정**: CSV 전체 행을 Claude에 보내 거래 JSON을 통째로 생성시키지 않는다. 대신 (1) 헤더 + 샘플 행(최대 10행)으로 컬럼 매핑 규칙만, (2) 고유 가맹점명 목록으로 카테고리만 Claude가 반환하고, 실제 행 단위 date/description/amount 추출은 코드가 매핑을 적용해 처리한다. 업로드 API는 동기 처리를 유지하고, 행 수 캡은 2,000행으로 둔다. `maxDuration`은 step 3 스파이크 실측 후 확정한다.
**이유**: 거래당 출력 토큰을 30~50으로만 잡아도 1,000행이면 출력이 3만~5만 토큰이 되어 응답에 수 분이 걸릴 수 있고, 출력이 길어질수록 JSON이 중간에 잘려 스키마 검증 실패로 업로드 전체가 실패할 위험이 커진다. 무료 업로드 1건당 Claude 비용도 무시하기 어려운 수준이 된다. 카드 명세서는 같은 가맹점이 반복되므로 고유 적요 수는 보통 행 수보다 훨씬 적어, 카테고리 분류만 Claude에 맡기면 출력 크기가 행 수와 거의 무관해진다.
**트레이드오프**: "Claude가 전부 처리"하는 것보다 코드가 조금 더 필요하다(범용 CSV 토큰화 라이브러리 도입, 매핑 적용 로직). 취소/환불 거래는 스킵만 하고 원거래를 상쇄하지 않아 지출 합계가 부풀 수 있다(알려진 한계).

### ADR-004: Polar 결제/구독, `checkout_pending` 미저장
**결정**: 결제/구독 처리에 Polar를 사용한다. 체크아웃 시작 시점에는 DB에 아무 것도 쓰지 않고, 결제 완료 웹훅이 도착해야만 `active`로 기록한다. 유료 권한 판정은 `status` 하나만이 아니라 `status`와 `current_period_end`를 함께 매 요청 시 파생 계산한다.
**이유**: Polar는 Merchant of Record라 세금·인보이스를 자동 처리한다. 체크아웃 중간 상태(`checkout_pending`)를 저장하지 않으면 사용자가 결제 페이지를 그냥 닫아도 영구 고착 상태가 생기지 않는다. 파생 판정을 쓰면 Polar가 결제 주기 종료 시점에 웹훅을 보장하지 않아도 안전하게 다운그레이드된다.
**트레이드오프**: 게이팅 로직이 단순 상태 비교가 아니라 별도 판정 함수가 되어 로직이 약간 늘어난다.

### ADR-005: Google OAuth 단일 로그인
**결정**: Supabase Auth의 Google OAuth만 지원한다. 이메일/비밀번호 로그인은 만들지 않는다.
**이유**: 비밀번호 저장·재설정·검증 로직을 지원할 필요가 없어 구현 부담과 보안 리스크가 줄어들고, 개인정보(비밀번호 해시) 저장을 최소화할 수 있다.
**트레이드오프**: Google 계정이 없는 사용자는 가입할 수 없다.

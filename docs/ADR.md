# Architecture Decision Records

## 철학
MVP 속도 최우선. 별도 인프라나 추상화보다 작동하는 최소 구현을 선택하되, 금융 데이터를 다루는 만큼 보안(격리·마스킹)은 타협하지 않는다. AI가 잘하는 일(비정형 데이터 정규화·분류)은 AI에게 맡기고, 손으로 짜야 할 코드는 최소화한다. 검증이 필요한 아키텍처 가정(지연시간, 토큰 사용량 등)은 배포 직전이 아니라 해당 기능을 구현하는 시점에 스파이크로 먼저 확인한다.

---

### ADR-001: Next.js App Router + Vercel CLI로 조기·잦은 배포
**결정**: Next.js 15 App Router를 사용하고, Vercel에 Vercel CLI(`vercel deploy`)로 배포한다. 기능이 없는 mock/스켈레톤 상태부터 가장 먼저 배포하고, 이후 각 개발 단계를 완료할 때마다 재배포한다.
**이유**: 랜딩/대시보드/API를 단일 배포 단위로 묶을 수 있고 Vercel과 궁합이 좋다. 조기·잦은 배포로 환경변수 누락, 함수 실행시간 제한 같은 배포 파이프라인 이슈를 개발 후반이 아니라 초반에 발견할 수 있다.
**트레이드오프**: Vercel 서버리스 함수의 실행시간 제약이 동기 CSV 분석과 상충할 수 있다 — `maxDuration`을 스파이크로 실측해 대응한다(ADR-004 참고).

### ADR-002: Supabase 단일 백엔드
**결정**: 인증(Google OAuth), 데이터베이스(Postgres), 파일 저장(Storage)을 Supabase 하나로 통합한다.
**이유**: MVP 속도가 최우선이라 별도 인프라를 관리할 필요가 없고, RLS로 사용자 간 데이터 격리를 선언적으로 구현할 수 있다.
**트레이드오프**: 벤더 락인.

### ADR-003: Google OAuth 단일 로그인 + 업로드 전 로그인 필수
**결정**: Supabase Auth의 Google OAuth만 지원하고 이메일/비밀번호 로그인은 만들지 않는다. 랜딩은 가치 설명 + 로그인 유도에 집중하고, 업로드는 대시보드에서만 가능하다(비로그인 체험 없음).
**이유**: 비밀번호 저장·재설정·검증 로직이 없어 구현 부담과 보안 리스크가 줄고, 개인정보(비밀번호 해시) 저장을 최소화할 수 있다. 원본 보관·히스토리·quota 강제·결제 귀속이 모두 사용자 식별을 전제로 한다.
**트레이드오프**: Google 계정이 없는 사용자는 가입할 수 없다. 로그인 마찰로 초기 이탈이 생길 수 있어 블러 페이월 등으로 전환 유인을 보완한다(ADR-006).

### ADR-004: CSV 파싱은 Claude에 위임, 2단계 호출
**결정**: 카드사별 파서를 코딩하지 않고, 서버에서 인코딩만 감지(EUC-KR/CP949 → UTF-8)한 뒤 Claude가 CSV 원문을 정규화된 거래 JSON으로 변환한다. 호출은 ①CSV→거래JSON 파싱(Haiku 4.5, 저장) → ②거래JSON→분류·요약(Sonnet 5/Opus 4.8) 두 단계로 나눈다. 처리는 동기 + 로딩 스피너.
**이유**: 한국 카드사 CSV는 표준이 없어(컬럼·헤더·인코딩 제각각) LLM이 정규화를 압도적으로 잘하고, 카드사 추가에 개발이 필요 없다. 파싱 결과를 저장하면 재분석·향후 인사이트에 재사용할 수 있고, 반복 노동(파싱)엔 싸고 빠른 모델을, "와"를 만드는 요약엔 좋은 모델을 써서 비용을 최적화한다.
**트레이드오프**: CSV 원문 전체를 보내므로 명세서가 크면 토큰 비용·컨텍스트 한도·JSON 잘림 부담. 대안으로 "헤더+샘플만 Claude가 매핑하고 행 변환은 코드"를 검토했으나, 파서 코드를 늘리는 대신 파싱 품질·개발 단순성을 택했다. 행 수 캡(2,000행)과 무료 월 3회 한도로 리스크를 제한하고, 백그라운드 큐는 쓰지 않아 대용량은 MVP 범위 밖이다.

### ADR-005: 원본 CSV까지 전부 저장 (개인화 재료 확보)
**결정**: 원본 CSV(Storage) + 정규화 거래내역 + 분석결과를 모두 저장. RLS·Storage 버킷 정책으로 사용자별 격리, Claude 전송 사본만 마스킹.
**이유**: 향후 개인화 서비스에는 원문이 필요하다. 히스토리 유료 혜택도 저장을 전제로 한다.
**트레이드오프**: 보관 데이터가 많아 유출 시 표면적이 커진다 → 격리·마스킹으로 상쇄.

### ADR-006: 과금은 사용량(quota) 제한 + 블러 페이월
**결정**: Free는 월 3회 업로드, Pro는 무제한 + 히스토리(단일 Pro 티어, 월 구독). 기능은 동일하고 사용량(quota)만 다르며 `is_pro` 불리언으로 분기한다. quota 소진 후 재업로드도 분석은 실행하되 결과를 블러 처리하고 업그레이드 CTA를 노출한다.
**이유**: 핵심 가치를 무료로 충분히 체험시켜 "와"를 먼저 주는 편이 전환율이 높고, 결과를 흐릿하게라도 보여줘야 열망이 생겨 전환된다. `is_pro` 하나로 분기해 구현도 단순.
**트레이드오프**: 다중 티어·연간 할인 LTV는 포기(향후 확장). 막힌 사용자에게도 Claude 비용이 발생하나 전환 가치가 이를 상회한다고 판단.

### ADR-007: Polar 결제/구독, `checkout_pending` 미저장
**결정**: 결제/구독 처리에 Polar를 사용한다. 체크아웃 시작 시점에는 DB에 아무 것도 쓰지 않고, 결제 완료 웹훅이 도착해야만 구독 레코드를 갱신한다. 유료 권한은 `is_pro` 불리언으로 분기한다.
**이유**: Polar는 Merchant of Record라 세금·인보이스를 자동 처리한다. 체크아웃 중간 상태(`checkout_pending`)를 저장하지 않으면 사용자가 결제 페이지를 그냥 닫아도 영구 고착 상태가 생기지 않는다. `is_pro` 단일 판정은 게이팅 로직을 가장 단순하게 유지한다.
**트레이드오프**: 결제 주기 종료 웹훅이 누락되면 유료 상태가 고착될 수 있다 — 웹훅 신뢰성에 의존하며, 필요 시 `current_period_end` 기반 파생 판정으로 강화할 수 있다(향후).

### ADR-008: 핵심 인사이트는 "지출 요약 + 자동 카테고리 분류"로 시작
**결정**: MVP 인사이트는 카테고리 자동분류(9종 고정) + 자연어 요약 + 월별 지출 추이에 한정. 이상탐지·Q&A는 향후.
**이유**: Claude가 가장 잘하는 일(가맹점명 → 카테고리)이라 적은 노력으로 확실한 "와" 순간을 준다.
**트레이드오프**: 능동적 코칭/대화형 경험은 포기. 차별화 여지를 뒤로 미룸.

### ADR-009: 다크 미니멀 + 앰버 포인트 색상
**결정**: 다크모드 고정, 무채색 베이스 + 포인트 색 앰버/골드 `#f59e0b`. 보라/인디고 등 AI 슬롭 배제(`docs/UI_GUIDE.md`).
**이유**: 금융에 어울리는 톤이며 초록(성공)·빨강(에러) 시맨틱과 충돌하지 않는다. "도구처럼 보이는" 제품 지향.
**트레이드오프**: 화려한 마케팅 비주얼은 포기.
